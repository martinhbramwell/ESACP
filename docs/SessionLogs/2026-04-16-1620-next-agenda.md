## Scope — what Phase 7 creates / reduces

1. `tools/cli/` directory with one file per command (~12 files). Each file ≤ 80 lines; only parses args, calls ONE pipeline primitive, formats output. No `subprocess.run`, no business logic.
2. `tools/api_models.py` — Pydantic request/response models lifted out of `api.py`.
3. `tools/api/routes/` (likely) — route modules grouped by resource (hosts, provision, destroy, power, jobs, health, template). `api.py` becomes FastAPI app wiring + middleware only.
4. `tools/esacp.py` reduced to argparse parser + dispatch table (import from `tools.cli`).
5. `tools/job_worker.py` reduced to argv parsing + single dispatch.

## Design questions to resolve up front

1. **Dispatch table placement** — two options:
   - (a) dispatch dict in `tools/esacp.py` mapping subcommand → callable.
   - (b) each `tools/cli/cmd_*.py` registers itself via a decorator.
   Prefer **(a)** — simpler, explicit, no import-order magic. Fits inside esacp.py's ≤150-line budget alongside argparse definitions.

2. **Where does `cmd_display_configuration`'s 115-line tree-render live?** It is pure CLI presentation — not business logic. Options:
   - (a) Leave it in `tools/cli/cmd_display_config.py` even though it exceeds the 80-line limit; request a ratchet exemption.
   - (b) Decompose: `cli/cmd_display_config.py` (dispatcher ≤ 30 lines) + `cli/display/config_tree.py` (tree-builder helpers ≤ 80 lines).
   - (c) Move the tree-builder to `tools/pipeline/stages/common/config_tree.py` as a query-only helper returning a structured dict, then render with Rich in the dispatcher.
   **Recommend (b)**. Presentation stays in `tools/cli/`, decomposed into ≤80-line units. Pipeline layer stays free of Rich.

3. **Is `cmd_destroy` (106 lines) in Phase 7 or Phase 8?** It still runs virsh + SSH + hosts_map edits directly. It duplicates `orchestration/destroy_vm.py` + bits of `macro/destroy.py`. The plan puts it in Phase 7, but extraction of the logic into the existing destroy primitive arguably belongs in Phase 8's "delete dead Gen 1 + extract trapped logic" scope. Proposal: for Phase 7, call the existing `macro/destroy.py` from the thin dispatcher — if there's a behavioural gap, note it for Phase 8 rather than growing Phase 7. Confirm at session start.

4. **Pydantic model extraction (`tools/api_models.py`)** — a single flat module, or a package `tools/api_models/` with one file per resource? At current api.py size (907 lines) there are likely ~8-12 models. **Flat module** first; split only if it exceeds 80 lines.

5. **`job_worker.py` thinning** — after phases 4-6, most of its business logic is in macros. Remaining 305 lines are mostly log-formatting, status-file writes, and the dispatch switch. Plan says ~50 lines achievable. Verify by inspection — don't invent work.

## Sequence of work (proposed)

1. Create `tools/cli/` + empty `__init__.py`.
2. **Thin commands first** — one file each for `cmd_verify_vpn`, `cmd_validate_observability`, `cmd_build_vm`, `cmd_provision`, `cmd_snapshot_vm`. Low risk, proves the pattern, instant `esacp.py` shrinkage.

4. **Medium commands** — `cmd_validate_keys`, `cmd_clear_known_hosts`, `cmd_confirm_prerequisites`, `cmd_destroy_vm`, `cmd_provision_vm`. Where subprocess calls remain, route through the nearest existing primitive.

6. **`api.py` split** — extract Pydantic models to `api_models.py`, then route groups to `api/routes/*.py`. `api.py` becomes the FastAPI app + `_spawn_job` only.
7. **`job_worker.py` trim** — remove any local logic that duplicates a macro.

## Risks / what could go wrong

- **Size of the change** — Phase 7 is the largest refactor in the Gen 3 plan. If the session is running long, split naturally at the api.py/job_worker.py boundary and defer the second half to a follow-up issue. Preserve 1:1:1 by proposing #195a / #195b in advance rather than mid-commit.
- **Hidden coupling between api.py routes and its internal helpers** — extracting routes first will expose which helpers are truly shared vs. route-local. Plan to also move shared helpers to `tools/pipeline/` if they contain logic.
- **Pydantic model import cycles** — if `api_models.py` imports from pipeline modules that import from api for types, break the cycle by keeping `api_models.py` dependency-free (only stdlib + pydantic).
- **Cytoscape e2e requires a running dev VM** — toshiba can host 1 dev VM at a time. If no VM is available, stand up `dev01` via the UI as the smoke test, then destroy it; this doubles as e2e validation of the thinned dispatchers.
