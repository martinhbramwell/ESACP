# Agenda — Next Session

**Objective:** Refactor ce_sri `install.py` — decompose the 1400-line monolith into focused, testable units.

---

## Context

`ce_sri/ce_sri/install.py` is 1400 lines with mutable globals, tangled exception handling, and functions that mix Frappe context operations with plain HTTP API calls. This is the root cause of #136 (bench execute deadlock) and blocks the zero-defect acceptance test.

## Priority

### 1. Decompose `after_restart` into standalone script

Extract the 5 functions called by `after_restart` (line 1337) into `tools/vm_scripts/h4g_after_restart.py`:
- `collectEnvironmentValues` — reads `common_site_config.json` + `apikey.sh` (no Frappe needed — just file reads)
- `loadInstallationParameters` — reads `ce_sri_parms.json` (file reads + validation)
- `confirmConnectionToERPNExtAPI` — `requests.get` to ERPNext API (plain HTTP)
- `installNodeJSService` / `configureNodeJSService` / `testNodeJSService` — npm, file writes, HTTP test
- `insertCustomScripts` — `requests.post` to ERPNext API (plain HTTP)

None of these need `frappe.local` — they all use `requests` or filesystem ops. The site name can come from `--site` CLI arg. The API key comes from `apikey.sh`.

**Change H4g in differentiate template** from:
```bash
bench --site $SITE_URL execute ce_sri.install.after_restart
```
to:
```bash
$BENCH_DIR/env/bin/python /tmp/vm_scripts/h4g_after_restart.py --site $SITE_URL --bench-dir $BENCH_DIR
```

### 2. Decompose `before_install` similarly

Same pattern — extract into `tools/vm_scripts/h4d_before_install.py`. H4d already works, but it shares the same fragile globals and would break the same way if any exception path changed.

### 3. Audit remaining `install.py` functions

Map every function in install.py:
- Which ones actually need Frappe context?
- Which are pure file/HTTP ops?
- Which share mutable globals?

Goal: install.py becomes a thin dispatcher that imports from focused modules, each under 50 lines.

### 4. Acceptance test

After #1, run `run-topology-test dev02 rebuild` — full destroy -> deploy -> inspect cycle. Zero errors. Close #135, #136, #116.
